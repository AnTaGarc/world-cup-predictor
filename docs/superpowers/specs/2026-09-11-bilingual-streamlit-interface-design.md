# Bilingual Streamlit Interface Design

## Objective

Turn the complete Streamlit interface into a contextually written Spanish/English product without changing sports data, model inputs, deep statistics, evidence, or audit records. The public-facing product title will be **Centro de análisis predictivo del Mundial 2026** in Spanish and **2026 World Cup Predictive Analytics** in English.

## Product behaviour

On the first visit from a browser profile, the application shows a focused language choice with two options: Español and English. No application page is rendered behind the choice. The selected language is stored in that browser and is reused on subsequent visits, reloads, new Streamlit sessions, application reruns, and Streamlit Cloud redeployments.

A persistent `ES | EN` control in the sidebar lets the visitor change language at any time. Changing it updates the current page immediately and replaces the stored browser preference. The initial choice is shown again only when browser storage is unavailable or has been cleared, in private browsing where storage is not retained, or on a different browser profile or device.

## Streamlit Cloud persistence

The browser preference is the source of truth between sessions. A small first-party Streamlit browser component reads and writes a namespaced `localStorage` value whose accepted values are only `es` and `en`. `st.session_state` mirrors the resolved language for fast reruns but is not treated as durable storage.

The application has three startup states:

1. **Resolving:** mount the browser component and withhold the main interface until its first result arrives.
2. **Unselected:** show only the bilingual language gate when no valid stored value exists.
3. **Resolved:** render the full interface and the sidebar language control.

Invalid or inaccessible browser storage is handled as an unselected preference, without an exception or an automatic language assumption. Browser storage contains no identity, sports data, or analytics data.

The component must work in the deployed Streamlit Community Cloud origin and in local Streamlit development. Its compatibility must be pinned through an explicit minimum Streamlit version rather than relying on whatever version Cloud happens to install.

## Internationalisation architecture

`src/wcpredict/ui/i18n.py` will own:

- the supported-language type and validation;
- the active-language lookup;
- semantic message keys and complete ES/EN catalogues;
- safe interpolation and plural-aware helpers;
- translations for controlled values such as statuses, tournament phases, confidence levels, positions, metrics, and table columns;
- catalogue completeness validation.

The existing `src/wcpredict/ui/translations.py` contains one-way Spanish presentation helpers. Its relevant mappings will be folded into or delegated to the new language-aware layer. Domain canonicalisation must remain language-independent: display labels must never be used as stored identifiers or model inputs.

Call sites use semantic keys instead of treating the Spanish source string as a translation key. Spanish and English copy is written independently for its product context. Dynamic messages use named parameters and language-specific templates. Count-sensitive content uses explicit singular and plural forms.

## Translation scope

The following are translated throughout every reachable page and state:

- page navigation and sidebar copy;
- headings, cards, captions, explanatory copy, tooltips, buttons, filters, tabs, segmented controls, expanders, empty states, warnings, errors, and success messages;
- dashboard, predictive analysis, scorelines, team statistics, player projections, data sources, history, calibration, data quality, knockout settlement, post-match capture, and closed-match audit interfaces;
- dataframe column names, chart titles and axes, metric labels, stage labels, status labels, controlled categories, and locally generated table cell labels;
- HTML assembled by Python for hero blocks, cards, tables, brackets, and audit layouts;
- user-visible fallback messages generated by the application.

Translations must use established football and analytics terminology. Examples include `Tiros a puerta` / `Shots on target`, `Marcador más probable` / `Most likely scoreline`, and `Portería a cero` / `Clean sheet`. Literal word substitution is not an acceptable implementation.

## Content that remains unchanged

Proper names remain canonical: national teams, players, stadiums, cities, official source names, and named statistical methods such as Dixon–Coles, Poisson, Elo, SofaScore, and StatsBomb.

Numbers and stored timestamps are not changed, although surrounding labels and date presentation may follow the selected language. Raw exception text from third-party libraries may be retained only inside a clearly localised technical-detail disclosure; primary error messages must be product copy from the catalogue.

## Source presentation and traceability

Provider identifiers are not appended to visible source headings. For example, `Dataset externo (mominullptr)` becomes `Dataset externo` in Spanish and `External dataset` in English. Similar parenthetical provider IDs are removed everywhere in the product interface.

Provider IDs, source URLs, import identifiers, timestamps, evidence links, and health records remain intact in storage and internal application objects. Where a dedicated technical audit table intentionally exposes a provider identifier as a data field, it may remain available under a localised column name; it must not be presented as decorative title copy.

## Data and audit safety

Internationalisation is presentation-only. It must not migrate or rewrite SQLite rows, JSON evidence, cached imports, deep-stat records, predictions, calibration history, model artefacts, or provider metadata. Repository methods, domain models, importers, collectors, and model calculations continue to consume canonical identifiers.

Closed-match audits retain all current metrics, comparisons, colour semantics, deltas, phase breakdowns, and evidence. Only their human-readable labels and explanatory copy change with the language.

## Page title and principal copy

The current slogan is removed. The hero uses the approved product title:

- ES: `Centro de análisis predictivo del Mundial 2026`
- EN: `2026 World Cup Predictive Analytics`

Supporting copy describes the actual analytical workflow in each language and contains no betting, odds, markets, expected-value, or bookmaker terminology.

## Testing and acceptance

Implementation follows test-driven development. Required automated coverage includes:

- supported-language validation and invalid-storage fallback;
- exact first-visit, returning-visit, and manual-switch state transitions;
- browser component read/write contract and namespaced storage key;
- parity of semantic keys and interpolation parameters between ES and EN;
- singular/plural cases and controlled-value translations;
- table-column and HTML-label localisation;
- absence of visible provider IDs in source headings;
- absence of the retired slogan and betting terminology from reachable interface code;
- protection against translated values entering persistence or model inputs;
- preservation of deep-stat and closed-match audit structures;
- Streamlit smoke tests in both languages.

A static interface contract will identify untranslated user-facing literals in the Streamlit UI modules, with an explicit allow-list for proper names and internal identifiers. This complements catalogue parity tests rather than replacing runtime tests.

Before release, both languages are exercised in the deployed Streamlit application. Visual verification covers the first-visit gate, sidebar switching, all top-level pages, long English labels, tables, cards, bracket content, player views, and audits. A normal reload and a fresh Streamlit session must return directly to the stored language without reopening the gate.

## Non-goals

- Translating stored source material or proper names.
- Adding more than Spanish and English in this iteration.
- Using automatic or runtime machine translation.
- Changing model behaviour, collected datasets, provider refreshes, deep statistics, audit calculations, or database schemas.
- Introducing accounts or server-side user profiles for language preferences.
